# OpenCode Documentation Harness

A set of 4 [OpenCode](https://opencode.ai) subagents to keep README, module documentation, charts, and the project thesis synchronized with actual code. None of the agents write numbers or claims they cannot point to in a concrete `.java` file — that constraint is in each agent's prompt.

## Installation

Copy these folders to your repo root (or merge if you already have `opencode.json`/`.opencode/`):

```
opencode.json
.opencode/agents/*.md
scripts/generate_charts.py
scripts/synthesize_thesis_context.py
scripts/build_thesis.sh
doc/thesis/*.md
doc/assets/           # regenerated by generate_charts.py, no need to copy
doc/modules/          # generated by doc-writer, no need to copy
```

Requirements in the environment where OpenCode runs: `python3` + `matplotlib` (`pip install matplotlib --break-system-packages`), and `pandoc` (`apt-get install pandoc` or your distro equivalent).

## Agents

| Agent | Role | Invoked with |
|---|---|---|
| `readme-writer` | Maintains `README.md` | `/readme-update` |
| `doc-writer` | Documents a package/module in `doc/modules/<package>.md` | `/docs-update <package>` |
| `chart-artist` | Recalculates charts in `doc/assets/` from code | `/chart-refresh` |
| `thesis-writer` | Updates chapters in `doc/thesis/*.md` and compiles `Tesis.docx` | `/thesis-build [focus]` |

You can also invoke them directly with `@agent-name` inside an OpenCode session instead of using the slash command.

## Typical Workflow

1. You changed code (added a `Transformer`, a `Diagnostic`, an enum value, etc.).
2. `/chart-refresh` — recalculates real metrics and regenerates PNGs in `doc/assets/`.
3. `/docs-update <affected package>` — updates that module's documentation, referencing the newly regenerated charts.
4. `/readme-update` — if the change affects overall structure or how the project builds.
5. `/thesis-build` — when you want a new version of the thesis `.docx` with up-to-date chapters and charts.

## How Charts Are Generated (No Invented Data)

`scripts/generate_charts.py` has no "magic" numbers: each `chart_*` function documents in a comment exactly which `.java` file the count comes from (e.g., transformer chain lengths per lexeme type, counted over `LexicalPreprocessors.java`). When code changes, the `chart-artist` agent updates that function and reruns the script — the PNG is never edited by hand.

```bash
python3 scripts/generate_charts.py            # regenerates all charts
python3 scripts/generate_charts.py --list      # lists available charts
python3 scripts/generate_charts.py enum_sizes  # regenerates a specific one
```

## How the Thesis Is Compiled

`doc/thesis/*.md` are concatenated in alphabetical file order (hence the numeric prefix `00-`, `01-`, ...) and passed through `pandoc`:

```bash
bash scripts/build_thesis.sh                  # generates Tesis.docx in root
bash scripts/build_thesis.sh --out other.docx  # different output name
```

The script validates before compiling that every image referenced with `![...](...)` in chapters exists physically, and aborts with the chapter name and missing image if not — so you never get a `.docx` with broken figures.

If your university requires a specific `.docx` style, generate a reference template with `pandoc -o doc/thesis/reference.docx --print-default-data-file reference.docx` (or export your own `.docx` with the styles you want pandoc to inherit) and the script will use it automatically via `--reference-doc`.

## Synthesis Pipeline (Modules → Thesis/README)

The harness uses a synthesis script to connect module documentation to the thesis and README:

```
doc/modules/*.md  --(synthesize_thesis_context.py)-->  doc/_synthesis_context.json
                                                              |
                                                              +--> thesis_view  --> thesis-writer (chapters 03, 04, 05)
                                                              +--> readme_view  --> readme-writer (architecture section)
```

### Module → Chapter Mapping

| Module | Thesis Chapter(s) | Key Content |
|---|---|---|
| `utils` | `03-architecture.md` | Repository (SymbolTable), LexemeInfo, Diagnostics, Builder/Director, Enums |
| `parser` | `05-syntactic-analysis.md` | Grammar, Publisher pattern, Initialization hierarchy, Grammar coverage |
| `lexer` | `04-lexical-analysis.md` | Transformer chains, Semantic analyzers, Diagnostics classification |

### Synthesis Script

`scripts/synthesize_thesis_context.py` reads all `doc/modules/*.md` and extracts:
- Mermaid diagrams
- Class tables (class, responsibility, pattern)
- Chart references (alt, path, caption)
- Section prose
- File trees
- How-to-test commands
- Initialization hierarchy (parser-specific)
- Grammar coverage (parser-specific)

Output: `doc/_synthesis_context.json` with two views:
- **thesis_view**: Full structured data for thesis-writer, plus `module_chapter_mapping`
- **readme_view**: Condensed architecture summary (pipeline Mermaid + key classes)

### Agent Integration

- **thesis-writer**: Runs synthesis script, reads `doc/_synthesis_context.json` (thesis_view), writes chapters in Spanish citing module data.
- **readme-writer**: Runs synthesis script, reads `doc/_synthesis_context.json` (readme_view), uses `pipeline_mermaid` and `key_classes` for architecture section, links to `doc/modules/`.
- **doc-writer**: Creates/updates `doc/modules/<package>.md`; notes which thesis chapters consume the content (see mapping above).
- **chart-artist**: Maintains `scripts/generate_charts.py`; charts referenced from modules and thesis.

## Adding a New Module Doc

Simply run:
```bash
/docs-update <package-name>
```
Example: `/docs-update lexer` creates `doc/modules/lexer.md` following the standard structure. The synthesis script will automatically pick it up on next run.
