# Abstract Syntax Tree Module Documentation

One-line description: The abstract syntax tree models the RULEBLOCK body of a function block as an immutable node hierarchy consumed by the lowering phase.

Last update: 2026-11-04

## Purpose

The `ast` package and its subpackages model the fuzzy rule block of a function block as an immutable tree of typed nodes. The parser builds the tree while reducing the `RULEBLOCK` grammar rules, through `parser.facades.RuleblockASTBuilder`, which maps the `parser.tree.ParserTreeNode` built during the reductions into `ast` nodes. The resulting `ast.AbstractSyntaxTree` is the input of the lowering phase, which turns it into the rule matrix of the code generator.

Every node extends `ast.AbstractAstNode` and answers with a semantic label. Labels are plain strings computed by each node; there is no separate label enumeration. Examples are `BODY`, `COND`, `IF`, `IS`, `NOT`, the name of the operator, the name of an identifier, the scoped rule-block name, and the program name. Nodes hold their attributes in private final fields and their children in an unmodifiable list.

The three packages have distinct roles:

| Package                   | Role                                          |
|---------------------------|-----------------------------------------------|
| `ast`                     | Base node and program root                    |
| `ast.ruleblock`           | Rule-block structure and identifiers          |
| `ast.ruleblock.operators` | Fuzzy operator enumeration and operator nodes |

`AbstractAstNode` copies and null-checks its child list in the constructor, then exposes it as an unmodifiable list. `AbstractSyntaxTree` is the root of a whole FCL program: it holds the rule blocks and returns the program name as its label. It does not expose a separate `programName()` accessor.

`RuleBlockNode` holds the scoped rule-block name, for example `MAIN#INFERENCE`, and the accumulation operator. The name is available through `label()`, not through a `name()` accessor. `WithNode` holds the weighting factor as a string, so it accepts both numeric literals and identifiers, and returns `WITH ` followed by that value as its label.

The concrete operator nodes `AsumNode`, `BdifNode`, `BsumNode`, `MaxNode`, `MinNode`, `NsumNode`, and `ProdNode` each fix one `Operator` constant. The parser builds generic `OperatorNode` instances configured with the operator selected in the source; the concrete subclasses are available as typed alternatives and are exercised by the AST unit tests.

The label is diagnostic and structural: it identifies the node in rendered trees and diagnostics. It is not an enum, and two different nodes may return the same label, as happens with two `IS` propositions.

## Logical Operators

`ast.ruleblock.operators.Operator` is the enumeration of fuzzy operators: `ASUM`, `BDIF`, `BSUM`, `MAX`, `MIN`, `NSUM`, and `PROD`. `OperatorNode` extends `AbstractAstNode` and holds one operator together with its operands; its label is the operator name.

`ast.ruleblock.operators.OperatorFactory` is a final utility class with a private constructor. Its static defaults match the grammar defaults:

| Operation    | Default | Source configuration                       |
|--------------|---------|--------------------------------------------|
| OR           | `MAX`   | `OR: MAX`, `OR: ASUM`, or `OR: BSUM`       |
| AND          | `MIN`   | `AND: MIN`, `AND: PROD`, or `AND: BDIF`    |
| Activation   | `MIN`   | `ACT: MIN` or `ACT: PROD`                  |
| Accumulation | `MAX`   | `ACCU: MAX`, `ACCU: BSUM`, or `ACCU: NSUM` |

The grammar builds the configuration list in the order OR, AND, activation, accumulation. `RuleblockASTBuilder` reads that list by index: 0 for OR, 1 for AND, 2 for activation, and 3 for accumulation.

## Construction from the Parser

The grammar rule `rule_block` reduces `RULEBLOCK rule_block_name operator_definition opt_activation_method accumulation_method rules_decl END_RULEBLOCK`. The semantic action appends the activation and accumulation operators to the OR and AND operators produced by `operator_definition`, wraps `rules_decl` in a `COMPONENT` parser node, and calls `RuleblockASTBuilder.build(componentNode, configuration)`.

`rule_block_name` returns `programName + '#' + IDENTIFIER`, so a rule block is scoped to its function block, for example `MAIN#INFERENCE`. The parser accumulates the resulting `RuleBlockNode` instances in `opt_rule_block_list`. When `function_block_declaration` reduces, it creates `new AbstractSyntaxTree(programName, ruleBlocks)`; the root is not created per rule block.

`parser.facades.RuleblockASTBuilder` traverses the parser tree and maps each `ParserLabel` to an AST node:

| Parser label   | AST node                               | Value taken from the parser tree                                   |
|----------------|----------------------------------------|--------------------------------------------------------------------|
| `IDENTIFIER`   | `ast_ruleblock_IdentifierNode`         | `symbolReference()`                                                |
| `IS`           | `ast_ruleblock_IsNode`                 | Two identifier children                                            |
| `ACTIVATION`   | `ast_ruleblock_operators_OperatorNode` | Activation operator from configuration index 2 and the conclusions |
| `BODY`         | `ast_ruleblock_BodyNode`               | The activation operator node                                       |
| `NOT`          | `ast_ruleblock_NotNode`                | The negated operand                                                |
| `OR`           | `ast_ruleblock_operators_OperatorNode` | OR operator from configuration index 0 and two operands            |
| `AND`          | `ast_ruleblock_operators_OperatorNode` | AND operator from configuration index 1 and two operands           |
| `CONDITION`    | `ast_ruleblock_CondNode`               | The condition child                                                |
| `IF`           | `ast_ruleblock_IfNode`                 | A condition node and a body node                                   |
| `WITH`         | `ast_ruleblock_WithNode`               | `symbolReference()` as weight and the wrapped if node              |
| `ACCUMULATION` | `ast_ruleblock_operators_OperatorNode` | Accumulation operator from configuration index 3 and the rules     |
| `COMPONENT`    | `ast_ruleblock_RuleBlockNode`          | `symbolReference()` as scoped name and the accumulation operator   |

`RuleblockASTBuilder.build` rejects a configuration list whose size is not four with `IllegalArgumentException`, and rejects a root that does not produce a `RuleBlockNode`. During traversal it also validates the expected arity and child types of each label and throws a `RuntimeException` for a malformed parser tree. A label outside the table yields `null`.

```mermaid

    participant T as ast.AbstractSyntaxTree

    participant R as lowering.constructors.RulesConstructor

    participant M as codegen.evaluation.MinMaxMethod

    P->>B: build(COMPONENT, configuration)
    B->>B: traverse ParserTreeNode
    B->>B: new RuleBlockNode and OperatorNode
    B-->>P: RuleBlockNode
    P->>T: new AbstractSyntaxTree(programName, ruleBlocks)
    P-->>C: getAST()
    C->>R: construct(controller)
    R->>L: adapt()
    L-->>R: int[] row
    R->>M: new MinMaxMethod(loweredRules)
```

The parser owns construction; the lowering phase only reads the immutable tree. `ControllerLower.newInstance` stores the root and creates `SymbolKeys` from `root.label()`, which is the program name.

## Lowering

`lowering.lowers.ControllerLower.adapt()` builds the `codegen.ControllerModel` from the symbol table and the AST. It runs three constructors in order: `BitWidthConstructor`, `FuzzyVariablesConstructor`, and `RulesConstructor`. The method returns `Optional.empty()` as soon as one constructor reports an unsupported program.

`lowering.constructors.RulesConstructor` is the part that consumes the rule-block AST. It accepts exactly one rule block, requires accumulation `ACCU: MAX`, and requires at least one rule. Each rule is lowered by `lowering.lowers.RuleLower.adapt()`, which returns one `int[]` row. The rows are collected into a `codegen.evaluation.MinMaxMethod`.

`RuleLower` builds a row with one column per input followed by one column per output. Each cell holds the index of the term in the variable's fuzzifier or defuzzifier parameter list; `-1` marks an unused cell. The accepted subset is narrower than the full grammar:

| Input construct                              | Accepted by `RuleLower`                                      |
|----------------------------------------------|--------------------------------------------------------------|
| Rule without `WITH`                          | Yes                                                          |
| Rule with `WITH`                             | Only when the weight compares equal to one as a `BigDecimal` |
| Condition `variable IS term`                 | Yes                                                          |
| Condition tree of `AND: MIN`                 | Yes, flattened recursively                                   |
| `OR` condition with `MAX`, `ASUM`, or `BSUM` | No                                                           |
| `AND` with `PROD` or `BDIF`                  | No                                                           |
| `NOT`                                        | No                                                           |
| Bare identifier as a condition               | No                                                           |
| Conclusion that is not `variable IS term`    | No                                                           |
| Repeated input or output variable            | No                                                           |
| Input or output not used by the rule         | No                                                           |

Problems are reported through `utils.DiagnosticsHandler`. Unsupported constructs produce `utils.diagnostics.UnsupportedFeature`. Undeclared variables, terms that do not belong to the variable, and repeated variables produce `utils.diagnostics.UndeclaredReference`. The model is built only when every rule lowers without a diagnostic.
